# 插桩接入

[简体中文](插桩接入.md) · [English](instrumentation.md)

更新日期：2026-10-22。插桩（代码里的 `peregrine-stub` / `PGStub`）让 Peregrine 直接读被测 App 进程里的视图树，而不是靠截图切分。接入后，页面名来自视图控制器，点击目标来自真实控件，探索结果更准确。

插桩是可选的。不接入时，Peregrine 用截图和系统快照识别界面，照常工作。模拟器上协议相同：Runner 与被测应用同在模拟器内走 `127.0.0.1`。电脑不能用 `iproxy` 预检，`cli.py stub` 打印 `skipped`，由 Runner 启动后探活。被测应用须为 `iphonesimulator` 包。真机与模拟器对照见[使用手册](handbook-cn.md#真机与模拟器)。

接入前确认：

- 你能修改并重新编译被测 App，并能把 Debug 包装到测试手机或已启动的模拟器上。
- 被测 App 用 CocoaPods 管理依赖。不用 CocoaPods 的接入方式见第 3 节。
- Peregrine 本身已按 [README](../README.md) 跑通过一次。

## 1. 快速接入

### 第一步：添加依赖

在被测 App 的 Podfile 里，给 App 的 target 加两行：

```ruby
target 'YourApp' do
  # ... 原有依赖
  pod 'peregrine-stub', :path => '<peregrine-ios 仓库>/Peregrine', :configurations => ['Debug']
  pod 'GCDWebServer', :configurations => ['Debug']
end
```

- `:path` 指向本仓库的 `Peregrine/` 目录（`peregrine-stub.podspec` 所在目录）。
- `:configurations => ['Debug']` 让插桩只进 Debug 包。测试包如果用别的构建配置（例如自建的 `Beta`），把配置名一起写进去。
- GCDWebServer 是插桩的依赖，podspec 已经声明，CocoaPods 会自动安装。单独再写一行，是因为 `:configurations` 不会传给依赖；不写的话，GCDWebServer 会被打进 Release 包。

如果 Podfile 里有 `use_frameworks!`，或者编译时报 `SDK does not contain 'libarclite'`，在 Podfile 末尾加上下面这段（已有 `post_install` 的话合并进去）。GCDWebServer 声明的最低系统版本是 iOS 8，新版 Xcode 不再支持低于 iOS 12 的部署版本：

```ruby
post_install do |installer|
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      if config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'].to_f < 12.0
        config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '12.0'
      end
    end
  end
end
```

然后执行：

```shell
pod install
```

不需要写任何代码。插桩随 App 启动自动加载，并且只在 Peregrine 启动 App 时才开服务（见第 4 节）。用户自己从桌面打开 App 时，插桩什么也不做。

### 第二步：把 Debug 包装到目标

用 Xcode 打开 `.xcworkspace`，选择测试手机或已启动的模拟器，以 Debug 配置运行一次（Product > Run）。装好后可以停止运行。模拟器必须编 `iphonesimulator` 包，嵌入的 framework 也必须是模拟器切片；装入真机切片时进程会立即退出，系统报 `have 'iOS', need 'iOS-simulator'`。

### 第三步：自检

在本仓库的 `Peregrine/` 目录执行通信检查，`9797` 可以换成任意空闲端口：

```shell
PEREGRINE_BUNDLEID=<被测 App 的 Bundle ID> PEREGRINE_DATAPORT=9797 \
xcodebuild test -workspace Peregrine.xcworkspace -scheme PeregrineRunner \
  -destination 'platform=iOS,id=<设备 UDID>' \
  -only-testing:PeregrineRunner/PeregrineRunner/testPingNetwork \
  DEVELOPMENT_TEAM=<Team ID> -allowProvisioningUpdates
```

十秒左右结束。日志里有 `stub success port 9797`，并以 `** TEST SUCCEEDED **` 结束，说明接入成功。看到 `stub failed port 9797` 时，按第 5 节排查。模拟器把 `-destination` 换成 `'platform=iOS Simulator,id=<UUID>'`。

也可以只用 Xcode 确认：在被测 App 的 scheme 里（Product > Scheme > Edit Scheme > Run > Arguments > Environment Variables）加一项 `stubPort`，值为 `9797`，运行 App。约 2 秒后，Xcode 控制台打印 `start peregrine stub listen success on 127.0.0.1:9797`。确认后记得删掉这一项。

### 第四步：开始探索

启动页的「数据端口」填 `9797`，再单击「开始」。命令行则多传一个 `PEREGRINE_DATAPORT`：

```shell
PEREGRINE_BUNDLEID=<被测 App 的 Bundle ID> PEREGRINE_DATAPORT=9797 PEREGRINE_DURATION=1 \
xcodebuild test -workspace Peregrine.xcworkspace -scheme PeregrineRunner \
  -destination 'platform=iOS,id=<设备 UDID>' \
  -only-testing:PeregrineRunner/PeregrineRunner/testPeregrine \
  DEVELOPMENT_TEAM=<Team ID> -allowProvisioningUpdates
```

日志里 `stub probe port 9797 alive 1 ... ui stub` 表示这一轮用的是插桩树。`alive 0` 表示没连上插桩，这一轮已退回截图识别。模拟器同样把 `-destination` 换成 `'platform=iOS Simulator,id=<UUID>'`。

真机上，启动页和 `tools/launch/cli.py run` 在开跑前先检测被测应用是否接入插桩、端口是否由它应答，结论写在日志首行；未接入或端口被其他应用占用时，本轮不传数据端口，直接用截图。也可以单独检测：启动页单击数据端口右侧的「检测」，或执行 `python3 tools/launch/cli.py stub --bundle-id <Bundle ID> --dataport 9797`。模拟器无法从电脑探测，启动页「检测」不可用，`cli.py stub` 打印 `skipped`，开跑后由 Runner 自行探活。结论的含义见 [使用手册](./handbook-cn.md) 的「插桩」一节。

## 2. 可选：不让某些视图进树

调试浮窗、水印、埋点面板这类视图会干扰探索时，可以把它们排除。写一个 `PGStub` 的子类，重写 `shouldExposeView:`；返回 NO 的视图连同子树都不进树。

子类代码必须包在 `#if DEBUG` 里。插桩只进 Debug 包，不包起来的话，Release 包会因为找不到 `PGStub` 而链接失败。

Objective-C：

```objc
#if DEBUG
#import "stub.h"

@interface MyStub : PGStub
@end

@implementation MyStub
- (BOOL)shouldExposeView:(UIView *)view
{
    if ([view.accessibilityIdentifier isEqualToString:@"debug-panel"]) {
        return NO;
    }
    return [super shouldExposeView:view];
}
@end
#endif
```

开了 `use_frameworks!` 时，`#import "stub.h"` 和 `#import <peregrine_stub/stub.h>` 都能用。

Swift：在 bridging header 里加 `#import "stub.h"`（建议也放在 `#if DEBUG` 里），子类要用 `@objc(名字)` 指定 Objective-C 类名，否则插桩按名字找不到这个类：

```swift
#if DEBUG
@objc(MyStub)
final class MyStub: PGStub {
    override func shouldExposeView(_ view: UIView) -> Bool {
        if view.accessibilityIdentifier == "debug-panel" { return false }
        return super.shouldExposeView(view)
    }
}
#endif
```

再告诉插桩用哪个子类，二选一：

- 在被测 App 的 Info.plist 里加键 `PGStubClass`，值为 `MyStub`。
- 启动探索时传入：`PEREGRINE_LAUNCHENV=PGStubClass=MyStub`。两处都写时，以这里为准。

名字写错或类不是 `PGStub` 的子类时，被测 App 的控制台打印 `peregrine stub class MyStub is not a PGStub subclass, using PGStub`，插桩改用默认规则，探索照常进行。

## 3. 不使用 CocoaPods 时

本仓库的 `Peregrine.xcworkspace` 里有一个 `peregrine_stub` scheme，编出来是 `peregrine_stub.framework`，已经把 GCDWebServer 链进去了。第 6 节的测试应用就是用这种方式接入的：

1. 在本仓库 `Peregrine/` 目录执行 `pod install`，用 Xcode 打开 `Peregrine.xcworkspace`，选 `peregrine_stub` scheme。真机目标选 Any iOS Device；模拟器另选对应 Simulator，再编一份。两种切片不能混装。
2. 把产物里的 `peregrine_stub.framework` 加到被测 App 的 target，在 General > Frameworks, Libraries, and Embedded Content 里选 Embed & Sign。
3. 这种方式下 framework 会进所有构建配置。发正式包前需要自己把它移除，或者为测试包单独建一个 target。

## 4. 端口怎么对上

被测 App 只在自己进程的环境变量里有 `stubPort`、且大于 0 时开服务，Debug 包也一样。这个变量由 Peregrine 在启动 App 时传入：

- `PEREGRINE_DATAPORT` 大于 0 时，如果 `PEREGRINE_LAUNCHENV` 里没有写 `stubPort`，Peregrine 自动补上同一个端口。所以只设 `PEREGRINE_DATAPORT` 就够了。
- App 收到 `UIApplicationDidFinishLaunchingNotification` 后 2 秒，插桩开始监听 `127.0.0.1:<端口>`，只接受本机连接。
- Peregrine 启动 App 后向这个端口探活，8 秒内每隔 0.4 秒重试一次。有一次成功就用插桩树，否则退回 `PEREGRINE_UI_SOURCE` 指定的来源。
- 探活成功后再发 `app_info` 核对应答方的 Bundle ID。插桩在 App 退到后台后仍监听端口，另一个接入插桩的 App 留在后台时会替被测 App 应答；Bundle ID 不一致时打 `stub port <端口> belongs to <Bundle ID>, not <被测 App>; stub not used`，本轮不用插桩。

Runner 和被测 App 在同一目标上，地址是目标自己的 `127.0.0.1`，不经过 Wi-Fi。真机从 Mac 预检才需要端口转发；模拟器上电脑不能用 `iproxy` 预检。

运行中由 `PGStubWatch` 盯着插桩：

- 一段空树里的第一棵，会在 4 秒内重新探活。App 被重启后插桩要 2 秒才重新监听，这一步能等到它。探活通过就马上再取一次树。
- 连续 5 棵空树时再探活一次。通过说明页面确实是空的，继续用插桩；失败就打 `stub lost on port <端口>`，本轮剩下的步数改用 `PEREGRINE_UI_SOURCE` 指定的来源。

每次取树最多等 4 秒，超时按空树算。

## 5. 常见问题

| 现象                                                       | 原因和处理                                                                                                                                                                                                                                               |
|----------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 自检打印 `stub failed port 9797`，或探索日志是 `alive 0`            | 依次检查：目标上装的是不是 Debug 包（或写进 `:configurations` 的那个配置），模拟器还须是 `iphonesimulator` 切片；被测 App target 的 Other Linker Flags 有没有带 `$(inherited)`；端口是否被占用（按第三步的 Xcode 方式运行，控制台会打印 `start peregrine stub listen failed`）；App 冷启动是否超过 6 秒（插桩在启动后 2 秒才监听，探活只等 8 秒） |
| Other Linker Flags 为什么要带 `$(inherited)`                  | 插桩靠 `+load` 自启动。CocoaPods 会在 `$(inherited)` 里加 `-ObjC`，让链接器保留没被直接引用的 `PGStub`。写死这个设置又不带 `$(inherited)` 时，链接器会丢掉插桩，编译不报错，但端口上没有服务                                                                                                                    |
| Release 编译报 `Undefined symbols ... _OBJC_CLASS_$_PGStub` | 子类代码没有包在 `#if DEBUG` 里，见第 2 节                                                                                                                                                                                                                       |
| 编译报 `SDK does not contain 'libarclite'`                  | Podfile 缺少第一步里的 `post_install`                                                                                                                                                                                                                      |
| Release 包里还能找到 GCDWebServer                              | Podfile 漏了 `pod 'GCDWebServer', :configurations => ['Debug']`                                                                                                                                                                                       |
| 被测 App 没接插桩，却填了数据端口                                      | 开跑前的检测给出 `stub check none`，本轮不传端口，直接用截图，不必等 8 秒探活超时                                                                                                                                                                                                 |
| 提示末尾有「已自动关闭原先占用该端口的 …」                                   | 另一个接入插桩、仍在后台的 App 占着端口，开跑前的检测已结束它的进程，本轮照常进行                                                                                                                                                                                                         |
| 日志首行是 `stub check other`，或 Runner 打 `belongs to … not …` | 端口被占用且未能自动关闭：占用方是旧版插桩、报不出 Bundle ID，或结束进程失败（原因写在提示里）。在目标上关掉其他接入插桩的 App，或给被测 App 换一个端口                                                                                                                                                               |
| 日志首行是 `stub check legacy`                                | 被测 App 里的插桩早于 `app_info`，能用但无法核对端口归属。重新 `pod install` 并编译 Debug 包即可升级                                                                                                                                                                               |
| 用户从桌面打开 App 时会不会开服务                                      | 不会。只有 Peregrine 启动 App 时才传入 `stubPort`                                                                                                                                                                                                              |
| 某个按钮在树里却从来不被点                                            | 按第 7 节的规则，它可能被判为不可点：控件禁用、祖先关了交互、在屏幕外，或者被上层视图完全盖住                                                                                                                                                                                                    |
| 子类没有生效                                                   | 看被测 App 控制台有没有 `is not a PGStub subclass`。Swift 子类要加 `@objc(名字)`                                                                                                                                                                                    |

## 7. 协议

Peregrine 由 `PGStubClient` 向 `http://127.0.0.1:<端口>/` 发 JSON-RPC 2.0，`id` 固定为 0：

```json
{"jsonrpc": "2.0", "id": 0, "method": "<方法>", "params": {}}
```

插桩不检查 `Content-Type`。请求体不是 JSON 对象时，按未知方法返回 `-32601`。`PGStubClient` 把短于 10 字节或不含 `result` 的响应当成失败。

| 方法             | 插桩的行为                                                                                                                                                                                                        | 谁在用                                        |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------|
| `kill_process` | 不进主线程，直接返回 `result: true`，进程不退出                                                                                                                                                                              | `PGStubWatch` 探活                           |
| `app_info`     | 不进主线程，返回 `result` 为 `{"bundle_id", "name", "version"}`，取自宿主 App 的 `Info.plist`                                                                                                                               | `PGStubWatch` 和启动页核对端口归属                   |
| `app_perf`     | 不进主线程，返回 `result` 为 `{"footprint_bytes", "cpu_percent", "threads", "main_max_ms", "main_slow", "memory_warnings", "thermal_state"}`，字段含义见使用手册「插桩端采样」。启动环境有 `stubPerf=1` 时随应用启动开始检测主线程，否则从第一次请求开始；10 秒没有请求后停止 | 开启 `PEREGRINE_PERF` 时 `PGPerfSampler` 每步一次 |
| `get_ui_tree`  | 在主线程建树，后台序列化，返回 `result` 为 `elem_info` 树的数组。主线程繁忙时排队的多个请求共用一次建树结果。建树抛异常时返回空数组                                                                                                                                | `PGStepScreen` 每一步取树                       |

其他方法名返回 `{"error":{"code":-32601,"message":"method not found"}}`。

`get_ui_tree` 的节点是 `{ "elem_info": {...}, "children": [...] }`。`elem_info` 含 `type`（视图类名）、`rect`（`left`、`top`、`width`、`height`，屏幕坐标，取整）、`identifier`、`label`、`value`、`visible`、`interactive`、`scrollable`、`clickable`，视图属于某个控制器时还有 `controller`。

隐藏或透明的视图连同子树不进树。`rect` 是裁到屏幕和 `clipsToBounds` 祖先之内的可见部分；裁空了 `visible` 为 false，开了 `clipsToBounds` 的视图裁空时整棵子树丢掉。

`clickable` 标启用的 `UIControl`、带按钮或链接无障碍特征的视图、列表行，以及自己带点击手势的视图。禁用的控件、不在屏幕上的视图，以及任一祖先关了 `userInteractionEnabled` 的视图都不标。父视图不会因为子视图能点中就变成可点。键盘、光标这些系统窗口不进树。

后加的兄弟视图画在上面。如果某个后加的兄弟视图（或它往下两层内的子视图）可见、能接收触摸、有不透明背景或类名含 `Dimming`，并且在屏幕上完全盖住一个视图，被盖住的视图连同子树都不标 `clickable`。所以弹出 `pageSheet` 时，底下页面的按钮仍在树里，但不可点。

页面名用内容控制器（例如 `Form`），跳过导航控制器和键盘控制器。同一层有多个分支时，从最后一个（最上层）往前找，所以弹出页显示时页面名是弹出页的控制器。

Runner 用整棵树的结构哈希做这一步的画面指纹，付费墙、广告、放大图门控和探索计分靠它判断画面是否变化；门控和元素匹配会先把树展平。

空树的计数在 `PGActionCycle`：返回的树字符串短于 20 计一次，连续超过 50 次发 `RESTART`。

## 8. 边界

- 插桩只读视图树。点击、长按和输入在节点能对上一个 `hittable` 的 `XCUIElement`、且两个矩形重叠至少一半时，由 `PGOperatePlayer` 直接作用在元素上。对不上、元素被挡住、元素操作抛错，以及滑动和返回，仍用坐标手势。键盘没有焦点时不调用 `typeText`。单次手势合成失败会被 `PGOperatePlayer` 接住，这一轮继续。
- 服务绑在目标的 `127.0.0.1`，没有鉴权，也不加密。只编进测试或调试包，不要进正式发布包。从 Mac 上直接访问真机要先做端口转发（例如 `iproxy 9797:9797`，再向 `http://127.0.0.1:9797/` 发请求）。Peregrine 自己跑在目标上，不需要转发；模拟器上电脑侧也不能用 `iproxy` 预检。
- `wifi_denied` 不影响这条链路，因为它不走 Wi-Fi。
